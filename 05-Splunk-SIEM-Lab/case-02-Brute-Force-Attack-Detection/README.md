# Case 1 - Brute Force Attack Detection
## Summary
An attacker repeatedly attempted to compromise the administrator account at Secorecode infotec. by guessing passwords until the correct credentials were identified. The attacker successfully authenticated to the server, resulting in a serious security breach. The incident could likely have been prevented by implementing basic security controls that were not in place.  

## Scenario
It is Monday morning at Securecode Infotech. The SOC team receives an alert about multiple failed login attempts targeting one of the production servers, EC2AMAZ-COTJ1IQ. As the analyst on duty, the task is to determine whether the activity is simply a user who forgot their password or something more serious.   
The investigation uses Windows authentication logs already loaded into Splunk to find out what happened, who did it, whether they got in, and what they did after. 

## Objective
Use Splunk to investigate the suspicious login activity, find the source of the attack, confirm if the attacker succeeded, trace where they went after getting in, and write up the findings clearly.

## Investigation Steps
## Step 1 — Load and Review Raw Logs
**Query Used:** `index="winserver" source="WinEventLog:Security" host="EC2AMAZ-COTJ1IQ"`   
This query retrieves Windows Security Event Logs from the winserver index that were generated by the host EC2AMAZ-COTJ1IQ.  
Since we are investigating a potential brute-force attack, we are primarily interested in authentication-related events. Filtering by the WinEventLog:Security source helps us focus on the relevant Windows Security logs and reduces unnecessary data, making the investigation more efficient.   

One of the first things to check is the ratio of failed to successful logins. A healthy network has very few failures. If failures are making up most of the events something is wrong.   

**Query Used:**`index="winserver" source="WinEventLog:Security" host="EC2AMAZ-COTJ1IQ" (EventCode=4625 OR EventCode=4624) | stats count by EventCode`   
During the last 24 hours, the server recorded 795 failed login attempts compared to 115 successful logins, resulting in a failed-to-successful login ratio of approximately 6.9:1.  
![img](https://github.com/s-anjeev/soc-projects/blob/main/05-Splunk-SIEM-Lab/case-02-Brute-Force-Attack-Detection/images/ratio.png)  

## Step 2 — Identify the Most Targeted Account
**Query Used:**`index="winserver" source="WinEventLog:Security" host="EC2AMAZ-COTJ1IQ" EventCode=4625 | stats count by Account_Name | sort -count`   

This query filters for failed Windows login attempts (EventCode 4625), counts the number of failed attempts for each username, and sorts the results in descending order, with the most targeted accounts appearing first.   
The purpose of this query is to determine how many failed login attempts were made against each user account. The results can help us determine whether the activity is more consistent with a brute-force attack, password-spraying attack, or legitimate user mistakes.  
![img](https://github.com/s-anjeev/soc-projects/blob/main/05-Splunk-SIEM-Lab/case-02-Brute-Force-Attack-Detection/images/admin-ailed-login-2.png)

## Step 3 — Identify the Attacking IP Address
**Query Used:** `index="winserver" source="WinEventLog:Security" host="EC2AMAZ-COTJ1IQ" EventCode=4625 | stats count by Source_Network_Address | sort -count`  

**What this does and why:** This narrows down to only failed logins against the admin account and groups them by where they came from. Knowing whether the attack is coming from one place or many changes how you respond. One IP means a single attacker using an automated tool. Multiple IPs could mean a botnet or a group working together.

Three source IP addresses were identified as responsible for the 21 failed login attempts against the Administrator account. The IP address 95.142.115.135 generated the highest number of attempts with 13, followed by 223.188.150.143 with 6, and 137.184.27.190 with 2.

## Step 4 — Reconstruct the Full Attack Timeline
**What this does and why:** This pulls all admin account activities both failures and successes
in time order. The moment failures turn into a success is the breach point.   

**What was found:** Two separate attack were trying to brute force at the same time.   
On August 25th, repeated failed login attempts against the Administrator account began from 223.188.150.143 at 08:54:15, followed by a successful login at approximately 09:04:36. A second IP, 95.142.115.135, continued repeatedly targeting the same account starting at 08:54:32.837.  

The fact that the second attack continued even after the first IP had successfully authenticated suggests these may have been two separate brute-force attempts, rather than a single coordinated attack. The repeated failures and successful authentication make this activity highly suspicious.

## Step 5 — Investigate the Second IP Address (95.142.115.135)
**Query used:**``

**What this does and why:** This pulls everything that 192.168.1.99 did in the environment. The goal is to understand if this IP was acting independently or in coordination with the primary attacker. The timing is the key thing to look at here.    

**What was found:**95.142.115.135 made 14 unsuccessful login attempts between 08:54:32.837 and 09:35:39.805. Meanwhile, 223.188.150.143 had already successfully authenticated at 09:04:36. The continued failed attempts from 95.142.115.135 after the successful login suggest that it was a separate brute-force attempt and that this attacker did not obtain the correct password.

## Recommended Actions

- **Reset the Administrator account password** immediately and invalidate any potentially compromised credentials.
- **Restrict or disable direct remote access to the Administrator account** where possible.
- **Enable account lockout or throttling policies** to limit repeated authentication attempts.
- **Enable MFA** for remote administrative access.
- **Restrict RDP/remote access** to trusted IP addresses or through a VPN/bastion host.
- **Block or investigate the identified source IPs** `223.188.150.143` and `95.142.115.135`.
- **Review successful logins from 223.188.150.143** and investigate the activity performed after authentication.
- **Hunt for additional authentication attempts** from the identified IPs across other systems.
